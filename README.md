# Pi QA Goal Guardian

TypeScript extension для Pi: фиксированный план действий, последовательное выполнение, checkpoint и попытка screenshot после каждой подзадачи. Один штатный agent loop, без дополнительных LLM-вызовов extension.

Поддерживается **Pi 1.5.2**, Node.js **>=22.19**. Модель и Browse MCP подключаются обычными средствами Pi.

## Установка

```sh
npm ci
npm run typecheck
npm test
npm run pi -- -e .pi/extensions/qa.ts
```

Для переноса нужны `.pi/extensions/qa.ts` и весь `src/` с сохранением относительных путей. Runtime-модуль `typebox` предоставляет Pi.

## Вход и запуск

В Pi передайте стандартный JSON с двойными кавычками:

```text
/qa-run {"scenario_id":"123","url":"https://example.com","task":"Заполни и отправь форму"}
```

Либо файл с тем же объектом:

```text
/qa-run test-case.json
/qa-run "directory with spaces/case.json"
```

Все три поля обязательны и являются непустыми строками; URL должен быть полным HTTP(S). Исходный текст task сохраняется без переписывания. Дополнительные поля отклоняются. **Миграция:** переименуйте прежний `id` в `scenario_id`, удалите `expected`, явно нужную проверку впишите в `task`. Старые кейсы несовместимы.

Весь остаток `/qa-run` — один JSON-документ или путь. Если он начинается с `{`, ошибка JSON не превращается в попытку загрузки файла. Невалидный ввод не заменяет загруженный сценарий. Команда запускает модель сразу; загрузка нового сценария допускается после settlement предыдущего.

Программный запуск: передавайте JSON одним элементом argv, без сборки shell-команды. Например, из Node.js:

```js
import { spawn } from 'node:child_process';
const scenario = { scenario_id: '123', url: 'https://example.com', task: 'Заполни и отправь форму' };
spawn(process.execPath, [
  'node_modules/@earendil-works/pi-coding-agent/dist/cli.js',
  '-e', '.pi/extensions/qa.ts', '--qa-case-json', JSON.stringify(scenario),
  '--no-session', '-p', 'Execute the loaded QA scenario.',
], { stdio: 'inherit' });
```

Для файла:

```sh
npx --no-install pi -e .pi/extensions/qa.ts --qa-case ./test-case.json --no-session -p "Execute the loaded QA scenario."
```

`--qa-case-json` и `--qa-case` только загружают сценарий; prompt запускает модель. Одновременное указание обоих флагов, пустой источник или невалидный startup-сценарий блокируют модель и инструменты. После терминального исхода prompts блокируются до нового `/qa-run` или reload/смены сессии.

Browse tools должны быть доступны в Pi. При явном ограничении `--tools` включите **qa_plan, qa_checkpoint, qa_finish** и необходимые Browse tools.

## Контракт инструментов

1. `qa_plan` один раз сохраняет полный план и сразу активирует S1:

```json
{"subtasks":[{"subtask_id":"S1","description":"Заполни и отправь форму"}]}
```

От 1 до 100 подзадач, последовательные ID `S1`, `S2`, …, description до 2000 символов. Текст и явно заданные значения сохраняет модель; extension проверяет формат и порядок, но не полноту декомпозиции. Начальная инструкция содержит оба согласованных примера: «заполни и отправь форму» — одна подзадача; «выбери X, введи Y, отправь» — три. Настройка промпта на реальной модели остаётся отдельной работой.

Ответ qa_plan содержит активный ID, описание S1 и допустимое следующее действие. Модель сразу выполняет S1 через Browse в текущем loop. Отдельный инструмент qa_execute_subtask удалён: активация остаётся внутренним переходом extension и не требует дополнительного вызова модели.

2. После действия модель вызывает:

```json
{"subtask_id":"S1","status":"passed","observation":"Форма отправлена, наблюдается переход на страницу результата","reason":""}
```

У `qa_checkpoint` status — passed/failed/blocked. Для passed нужна непустая observation, для failed/blocked — непустая reason; оба поля до 1000 символов. Неправильные аргументы исправимы и не меняют состояние. Дубликат не создаёт новую ревизию или screenshot. Старый контракт с `completed`/`current_objective` больше не принимается: прогресс строится extension из результатов.

После принятия checkpoint extension закрывает обычные действия, сохраняет результат, ожидает диагностическую попытку и только затем при passed автоматически активирует следующую подзадачу в executing. Ответ checkpoint уже содержит её ID, описание и допустимое следующее действие; модель сразу продолжает работу через Browse. До возврата диагностики действия закрыты. При пользовательском abort следующая подзадача не активируется. При failed/blocked автоматически завершает весь run; оставшиеся подзадачи не выполняются. Внутренний screenshot допускается по происхождению вызова Pi и ожидающему checkpoint, а не только по имени инструмента.

3. После всех passed модель вызывает `qa_finish` отдельно:

```json
{"verdict":"passed"}
```

Модель не генерирует evidence в qa_finish вообще и не передаёт reason при passed. Поле evidence отчёта extension собирает из сохранённых observations; reason при passed остаётся пустой строкой. Для аварийного blocked передаётся только verdict и обязательная непустая reason, без evidence. Дополнительной финальной стадии браузерных проверок нет. До плана допустим аварийный `qa_finish(blocked)` с конкретной причиной; во время подзадачи failed/blocked оформляются её checkpoint.

Стадии: `planning → executing → checkpointing → executing / awaiting_finish → terminal`. Browser tools запрещены до принятия плана, во время checkpointing и после последней подзадачи. Гейт активации проверяется кодом; стадии ready и отдельного activation round-trip больше нет. QA tools последовательные; порядок проверяется перед каждым фактическим вызовом, включая смешанные пакеты. При terminal все дальнейшие инструменты блокируются, на `turn_end` Pi получает abort после формирования результатов пакета.

## Результат без expected

`passed` означает заявленное моделью выполнение заданных действий и явно запрошенных проверок. Нужно наблюдать непосредственный результат действия; отсутствие tool error недостаточно. Для «нажми Отправить» не добавляется проверка БД. Для «проверь запись в списке» эта проверка обязательна.

`failed` — наблюдаемое невыполнение действия или заданной проверки.

`blocked` — редкий крайний исход: конкретное сохраняющееся препятствие, недостающие обязательные данные/доступ или необходимость внешнего вмешательства. Одна ошибка инструмента, загрузка страницы, закрытый dropdown, элемент вне viewport или старый locator не завершают подзадачу автоматически. Инструкция требует одну подходящую безопасную попытку восстановления и оценку результата. При отсутствии credentials или CAPTCHA бессмысленный обход не нужен. В reason указываются препятствие, восстановление и результат либо почему безопасной попытки нет.

После неизвестного исхода отправки модель сначала восстанавливает наблюдение; потенциально выполненную отправку/создание повторять нельзя. Неизвестный исход нельзя объявить passed. Редкость blocked задаётся инструкцией модели, без квот и эвристического анализа текста причины кодом; соблюдение на вашей квантованной модели требует target-проверки.

## Контекст

Исходный сценарий, план, текущий ID и результаты находятся в памяти extension вне истории модели. В системную секцию перед каждым запросом вставляется только стадия, актуальное действие, позиция, последнее observation и следующий допустимый инструмент. Полный план повторно не вставляется; tool responses также компактны. После compaction состояние восстанавливается из extension.

Это не удаляет накопленную историю Browse. Используется штатная compaction Pi, без удаления произвольных tool-call/result пар. Reload/смена сессии завершает незаконченный сценарий как incomplete. Восстановления после перезапуска процесса нет. Extension с принудительным `systemPrompt` может перекрыть структурированные секции Pi и требует адаптации.

## Диагностические скриншоты

После каждого принятого checkpoint — одна попытка screenshot, включая failed/blocked. Во время QA самостоятельный вызов screenshot моделью запрещён кодом, включая вложенный вызов через другой tool. Допускается только внутренний screenshot текущего checkpoint. Используйте DOM и текстовые observations; visual model не нужна. Этот gate проверяет вызовы инструментов, а не произвольный JavaScript внутри Browse execute. Уникальный инструмент `screenshot` (возможен MCP-префикс) должен иметь обязательный `tab`. Аргументы: `{tab, format: "png"}`. Вкладка берётся из последнего успешного Browse-ответа того же namespace или его аргументов. Случайный выбор вкладки, дополнительные `tabs` и повторы не выполняются. Режим Browse только с execute/status/tabs без plain screenshot для автосъёмки не подходит.

```text
qa-diagnostics/<run_id>/checkpoint-001.png
qa-diagnostics/<run_id>/checkpoint-002.png
qa-diagnostics/<run_id>/events.jsonl
```

Флаг `--qa-diagnostics-dir` меняет каталог. Если tool/tab неизвестны, попытка пропускается с отдельным логом. Ошибка screenshot или сохранения изображения не отменяет checkpoint и не меняет verdict. Abort signal ограничен 10 секундами, но backend должен его соблюдать; жёсткой отмены зависшего backend нет. Пользовательский abort во время диагностики сохраняет уже принятый failed/blocked; ошибка хранения отчёта имеет приоритет как error.

Изображения сохраняются только для человека. Image-блоки, их дубли в metadata/JSON и data-image URI очищаются перед моделью и compaction. Пиксели и диагностические пути не добавляются в QA-отчёт или системный прогресс. Проверки используют текст/DOM.

## Автоматическое закрытие QA-вкладки

При любом завершении run — passed, failed, blocked, incomplete, error или пользовательском abort — extension делает одну попытку закрыть известную QA-вкладку. После checkpoint закрытие выполняется после диагностической попытки screenshot и сохранения терминального результата. При техническом завершении без checkpoint дополнительный screenshot не добавляется.

Нужен доступный через Pi уникальный tab-scoped инструмент с именем close, close_tab или tab_close (возможен MCP-префикс), обязательным аргументом tab и без других обязательных аргументов. Используется последняя вкладка из успешного Browse-вызова того же namespace. Закрытие работает и без screenshot tool. Если модель уже закрыла эту вкладку, повторного закрытия нет. Другие вкладки и весь браузер extension не закрывает.

Внутренний close проходит Pi hooks с отдельным допуском на один вызов для сохранённого tab. После terminal прямой close от модели блокируется, как остальные действия. При abort используется отдельный, ещё не отменённый signal с пределом 5 секунд. Функция закрытия не создаёт новых запросов к модели.

События tab_close_succeeded / tab_close_failed / tab_close_skipped пишутся в qa-diagnostics/<run_id>/events.jsonl. Ошибка закрытия не меняет QA-verdict и не запускает повтор. Как и screenshot, фактическая отмена зависит от backend; принудительное убийство процесса выполнить cleanup не позволяет. На реальной Browse-прокси закрытие нужно проверить отдельно. Reload и штатный shutdown также вызывают cleanup, если run ещё не был очищен.

## JSON-отчёт

`qa-results/<run_uuid>.json`, каталог меняется `--qa-results-dir`. Сохранение атомарное через временный файл и переименование. Отчёт записывается при изменениях состояния и settlement. Идентификатор сценария не используется как имя файла. Наличие файла не означает завершения: дождитесь терминального execution_status.

| Поле | Содержание |
|---|---|
| `schema_version` | `2` |
| `run_id`, `scenario_id`, `test_case` | Запуск и неизменный вход без expected |
| `execution_status` | running / completed / incomplete / aborted / error |
| `stage`, `active_subtask_id` | Стадия и активное действие |
| `plan` | Фиксированные ID и descriptions |
| `subtask_results` | Упорядоченные status, observation, reason, revision, source |
| `progress` | Выведенные из результатов completed ID, следующая цель и последнее observation |
| `reported_verdict`, `verification_status` | Заявление модели; agent_reported при verdict, иначе not_evaluated |
| `verified_verdict` | Всегда null |
| `evidence`, `reason` | Сохранённые observations и причина исхода |
| `started_at`, `ended_at`, `duration_ms` | UTC и длительность |

Подзадачи plan без результата остаются pending; они не считаются выполненными. revision связывает результат с checkpoint-NNN в отдельной диагностике. Ошибка записи отчёта закрывает gate как error; если каталог недоступен, финальный JSON не гарантируется. Отсутствие отчёта — технический сбой даже при exit code 0 у Pi.

Телеметрия сохраняет llm_calls (before_provider_request, без внутренних transport retries), tool_calls, tool_executions (разрешённые вызовы), tool_errors, blocked_tool_calls и post_finish_attempts. Диагностические вызовы проходят Pi hooks и учитываются. post_success_actions/repeated_side_effects/goal_drift_events равны null: независимого измерения этих показателей нет.

Gate проверяет последовательность, но не истинность observations. `passed` не означает independently verified success. Extension не является sandbox и не отменяет side effects внутри уже запущенного Browse execute. Не запускайте lifecycle tools через параллельный вложенный executor: уже выполняющиеся операции нельзя отозвать. Неожиданное убийство процесса может оставить последний отчёт running.

## Проверки

`npm test` использует настоящий Pi AgentSession с локальным детерминированным stream вместо внешней модели. Проверяются порядок, смешанные пакеты, checkpoints/диагностика, abort, ошибки хранения, JSON/file ввод, compaction, retry и терминальные ограничения. `npm run typecheck` проверяет TypeScript.

Реальный Ascend endpoint, качество декомпозиции квантованной модели и реальная Browse-прокси этими тестами не проверяются. Начните target-проверку с короткого сценария, затем сравните длинный проблемный сценарий с baseline в новой сессии.
