# Pi QA Goal Guardian

Небольшая TypeScript extension, которая сохраняет исходную QA-задачу, возвращает модели последний checkpoint прогресса и завершает запуск через `qa_finish`. Pi управляет agent loop, Browse MCP — браузером. Собственных LLM-вызовов extension не делает; checkpoint является дополнительным tool call внутри штатного loop Pi.

Проверенная версия: **`@earendil-works/pi-coding-agent@1.5.2`**, Node.js **>=22.19**. Совместимость с Pi 0.x не заявляется. Пользовательские модели, inference endpoints и Browse MCP-прокси настраиваются обычными средствами вашего Pi; здесь их конфигурация не меняется.

## Установка и проверка

В каталоге проекта:

```sh
npm ci
npm run typecheck
npm test
npm run pi -- --version
```

Pi устанавливается локально в `node_modules`, глобальная установка не нужна. В другом окружении скопируйте проект без `node_modules` и выполните `npm ci` заново.

Для переноса в существующий проект Pi нужны **оба** каталога: `.pi/extensions/qa.ts` и весь `src/`, включая `qa-extension.ts`, `qa-state.ts`, `qa-diagnostics.ts`, с сохранением относительных путей. Для runtime используется предоставляемый Pi модуль `typebox`. Локальные зависимости нужны для разработки и проверок.

## Запуск

Интерактивный режим, явная загрузка extension:

```sh
npm run pi -- -e .pi/extensions/qa.ts
```

В Pi:

```text
/qa-run test-case.json
```

Команда загружает кейс и отправляет модели задание на выполнение. Путь с пробелами можно передать целиком в кавычках. Пути разрешаются от рабочей папки Pi. `.pi/extensions/qa.ts` также поддерживает стандартную автозагрузку после доверия проекту в Pi.

Для одного запуска из QA-платформы:

```sh
npx --no-install pi -e .pi/extensions/qa.ts --qa-case ./test-case.json --no-session -p "Execute the loaded QA case using Browse and finish with qa_finish."
```

Можно указать каталог отчётов:

```sh
npx --no-install pi -e .pi/extensions/qa.ts --qa-case ./test-case.json --qa-results-dir ./qa-results -p "Execute the loaded QA case."
```

`--qa-case` только загружает кейс; prompt запускает модель. В интерактивном режиме вместо флага удобнее `/qa-run`. После завершения любой дополнительный prompt блокируется до нового `/qa-run` или явной смены/reload сессии. Один процесс выполняет один активный кейс одновременно.

В target-окружении Browse MCP должен быть подключён и доступен модели. Если вы используете `--tools` с явным списком разрешённых инструментов, включите **`qa_checkpoint` и `qa_finish`** вместе с инструментами Browse. Extension не открывает браузер сама.

## Входной кейс

```json
{
  "id": "TC-001",
  "url": "https://example.com",
  "task": "Open the page and check its main heading.",
  "expected": "The main heading is Example Domain."
}
```

Все четыре поля обязательны и должны быть непустыми строками. Поддерживаются HTTP(S) URL. Исходный текст `task` и `expected` не обрезается и не переписывается. Некорректный `/qa-run` не заменяет уже загруженный кейс; некорректный `--qa-case` блокирует запуск модели и инструментов.

## Что делает extension

- Хранит неизменный кейс вне истории модели.
- Добавляет исходный кейс и короткие QA-правила в системные секции Pi через `before_agent_start`.
- Добавляет последний checkpoint через `context_with_system` как именованную секцию начального системного сообщения, сохраняя declarations инструментов и историю. После результата браузера новое сообщение `user` не добавляется.
- Регистрирует `qa_checkpoint`, чтобы модель сохраняла сделанное и текущую цель после значимого этапа. Прогресс не выводится автоматически из Playwright-кода.
- Регистрирует `qa_finish` с `verdict`, `evidence`, `reason`.
- Закрывает допуск всех дальнейших инструментов сразу после принятого finish, сохраняет JSON и останавливает запуск после завершения текущего пакета результатов.
- Отдельно фиксирует технические исходы, если агент завершился без `qa_finish`.

Пример вызова модели:

```json
{
  "verdict": "passed",
  "evidence": "The browser observation shows the heading Example Domain.",
  "reason": ""
}
```

Для `passed` нужна непустая `evidence`; для `failed` и `blocked` — непустая `reason`. Неправильный finish оставляет запуск активным, чтобы модель могла исправить аргументы.

## Прогресс и текущая задача

Модель вызывает `qa_checkpoint` после значимого этапа или перед паузой, например:

```json
{
  "completed": ["Creation form opened", "Required fields filled"],
  "current_objective": "Submit the form and observe the result",
  "observation": "Submit button is enabled"
}
```

`completed` — компактное накопительное резюме сделанного, до 20 строк по 300 символов; `current_objective` — обязательная текущая незаконченная задача, до 500 символов; `observation` — необязательное наблюдение, до 1000 символов. Если этапов много, модель объединяет ранние этапы в короткие резюме. Каждый checkpoint заменяет предыдущий снимок, а не добавляет старые цели в контекст.

Перед следующим LLM-вызовом системный контекст содержит `QA PROGRESS (agent_reported)` с этими полями и номером `revision`. Пока нового checkpoint нет, секция остаётся неизменной. До первого checkpoint секция прогресса отсутствует: extension не сообщает модели, что предыдущий прогресс недостоверен, и не подталкивает её к повторной проверке.

Это прогресс, **заявленный моделью**. Checkpoint не подтверждает выполнение этапов независимо и не выставляет финальный verdict. Модель сама выбирает значимые точки сохранения; checkpoint после каждого browser call не требуется. При compaction снимок возвращается из памяти extension, даже если сообщения с ним удалены из истории.

Политика проверок: модель продолжает с `current_objective` и проверяет только результат последнего действия или текущую цель. Если результат browser tool уже показывает нужный исход, дополнительный вызов для проверки не нужен. `completed` служит памятью о сделанном, а не списком для повторной валидации. К конкретному прошлому этапу можно вернуться при явном требовании тест-кейса либо при ошибке, потере состояния или противоречащем состоянии страницы. Финальный `expected` оценивается по доступным наблюдениям без повторного прохождения сценария. Это инструкция модели; extension не классифицирует и не блокирует отдельные проверки внутри Browse `execute`.

Для этой версии используйте структурированные prompt sections Pi. Другая extension, возвращающая принудительный `systemPrompt` из `before_agent_start`, может перекрыть системные секции, включая прогресс; такая комбинация не поддерживается без адаптации.

## Скриншоты только для человека

Модель использует DOM и текстовые observations. После успешного сохранения каждого `qa_checkpoint` extension сама делает одну попытку снять viewport через существующий Browse screenshot tool. Дополнительного LLM-вызова для этого нет. Невалидный checkpoint и `qa_finish` сами по себе съёмку не запускают.

Инструмент находится в живом каталоге Pi по имени `screenshot` (с возможным MCP-префиксом) и схеме с обязательным `tab`. Используется [официальная схема Browse](https://github.com/anomalyco/browse/blob/dev/rust/crates/browse-capture/src/screenshot.rs): `{tab, format: "png"}`, без `path`, чтобы получить MCP image и сохранить его на стороне extension даже при удалённом браузере. Из нескольких подходящих screenshot tools extension не выбирает случайный. Режим Browse, в котором доступны только `execute/status/tabs`, для автоматической съёмки не поддерживается: plain screenshot должен быть доступен через вашу прокси или настройку MCP.

Вкладка берётся из последнего успешного Browse-вызова того же namespace: `tab` в структурированном/JSON-ответе или protocol header, затем `tab` аргументов. DOM страницы не используется для угадывания вкладки. Дополнительный вызов `tabs` не делается. Если инструмент или вкладка ещё неизвестны, съёмка пропускается.

Файлы лежат отдельно от QA-отчётов:

```text
qa-diagnostics/<run_id>/checkpoint-001.png
qa-diagnostics/<run_id>/checkpoint-002.png
qa-diagnostics/<run_id>/events.jsonl
```

Каталог меняется флагом `--qa-diagnostics-dir`. Он добавлен в `.gitignore`. Ошибки съёмки/записи записываются только в отдельный `events.jsonl`, насколько это позволяет файловая система. Повторных попыток нет; screenshot failure не отменяет checkpoint и не меняет QA verdict. Вызов получает отдельный abort signal с пределом 10 секунд; реальная отмена зависит от соблюдения сигнала backend-инструментом.

Hook `tool_result` сохраняет image-блок и заменяет screenshot-ответ коротким текстом без пути к файлу. Дубли изображений в details/structuredContent удаляются. Перед основным модельным запросом image-блоки также убираются из копии контекста, включая старые сообщения с изображениями. Возвращаемые в текстовых наблюдениях data-image URI и JSON media очищаются; подготовленные сообщения для compaction проходят тот же фильтр. Текстовые DOM-описания изображений без пиксельных данных сохраняются. Пиксели не используются для подтверждения прогресса.

В JSON QA-отчёт не добавляются скриншоты, base64, пути и ссылки на них. Диагностический вызов проходит стандартные Pi hooks и поэтому учитывается в общих счётчиках tool calls/errors. Дополнительные browser operations для скриншотов происходят только при checkpoint; уже возвращённые другими инструментами изображения также сохраняются отдельно и фильтруются.

## JSON-результат

Файл: `qa-results/<run_uuid>.json`. Имя не строится из `case_id`; повторный запуск того же кейса создаёт отдельный файл. Запись выполняется через временный файл и переименование. Файл сохраняется при checkpoint, finish и после полного settlement. **Наличие файла не означает завершения:** при checkpoint `execution_status` равен `running`, `ended_at` — `null`; платформе нужно дождаться терминального статуса.

Основные поля:

| Поле | Значение |
|---|---|
| `schema_version` | `1` |
| `run_id`, `case_id`, `test_case` | Запуск и неизменная копия кейса |
| `execution_status` | `running`, `completed`, `incomplete`, `aborted` или `error` |
| `reported_verdict` | Заявленный моделью `passed`, `failed`, `blocked`; иначе `null` |
| `verification_status` | `agent_reported` при finish, иначе `not_evaluated` |
| `verified_verdict` | Всегда `null` в текущей версии |
| `progress` | Последний checkpoint с `completed`, `current_objective`, `observation`, `source: agent_reported`, `revision`; до первого checkpoint — `null` |
| `evidence`, `reason` | Evidence модели и причина исхода |
| `started_at`, `ended_at`, `duration_ms` | UTC timestamps и длительность до терминального решения |

**`reported_verdict: passed` не означает независимо проверенный успех.** Платформа должна учитывать `execution_status` и `verification_status`, не преобразовывать заявление модели в verified passed. При ошибке сохранения gate остаётся закрытым, а Pi получает error tool result. Если каталог недоступен, наличие JSON-файла не гарантируется; отсутствие отчёта нужно считать техническим сбоем, даже если процесс Pi завершился с кодом 0.

Телеметрия:

| Поле внутри `telemetry` | Что реально наблюдается |
|---|---|
| `llm_calls` | События `before_provider_request`; внутренние transport retries не считаются |
| `tool_calls` | События `tool_call` после валидации аргументов Pi |
| `tool_executions` | Вызовы, пропущенные gate, включая QA-инструмент; не внутренние Playwright-операции |
| `tool_errors` | Ошибочные `tool_execution_end`, включая блокировки gate |
| `blocked_tool_calls` | Вызовы, заблокированные gate |
| `post_finish_attempts` | Попытки tool calls после закрытия gate, включая техническое завершение |
| `post_success_actions`, `repeated_side_effects`, `goal_drift_events` | `null`: независимо наблюдать эти метрики extension не умеет |

## Остановка и ограничения

`qa_finish` объявлен `executionMode: "sequential"`: Pi 1.5.2 выполняет весь содержащий его пакет последовательно. Вызовы **до** finish могут выполниться; вызовы **после** finish блокируются. После сохранения всех результатов пакета `turn_end` вызывает `ctx.abort()`, так как одного `terminate: true` недостаточно для смешанного пакета. QA-отчёт сохраняет `completed`; технический abort Pi здесь является механизмом остановки. В истории Pi может появиться служебное aborted-сообщение, без нового запроса к provider.

После терминального исхода `input` перехватывает новые prompts до начала pre-prompt compaction, `session_before_compact` отменяет summarization, а `cache_warming_decision` прекращает будущий cache warming. Уже выполняющийся внешний запрос эти hooks не откатывают. Отмена в `before_provider_request` использует abort signal: исключения из этого hook Pi перехватывает, поэтому они не могут служить блокировкой. Гарантии предполагают, что provider соблюдает стандартный сигнал отмены Pi.

Ограничения проверенной гарантии: это прямые вызовы инструментов в одном основном пакете Pi. Не вызывайте `qa_finish` из параллельно работающего вложенного инструмента/codemode: уже запущенную параллельную операцию extension отозвать не может. Extension не является security sandbox.

Gate не отменяет side effects внутри уже выполняющегося Browse `execute`. Действия до finish модель всё ещё может повторять. Watchdog, бюджеты, независимая проверка evidence и вычисление качества A/B пока не реализованы. Неожиданное убийство процесса не гарантирует итоговый отчёт; последний checkpoint может остаться в JSON со статусом `running`. Автоматическое восстановление браузерного сценария после перезапуска не поддерживается.

При compaction состояние сохраняется в памяти extension. Reload/смена сессии завершает незаконченный кейс как `incomplete`; автоматически возобновлять браузерные действия extension не будет.

## Проверки

`npm test` запускает модульные тесты и интеграцию с **настоящим Pi AgentSession**. Только внешняя модель заменена детерминированным stream; инструменты, hooks, loader и JSON-запись работают реально. Проверяются смешанные пакеты finish/browser, отсутствие новых user-сообщений между browser calls, замена текущей цели через checkpoint, сохранение прогресса после compaction, ошибки инструментов и записи, повторные запуски, malformed input, настоящий abort, reload, отмена compaction/cache warming и восстановление после автоматического retry Pi.

Эти тесты проверяют передачу контекста и управление lifecycle. Они не доказывают, что реальная модель перестала зацикливаться. Для проверки регрессии используйте новую сессию с тем же проблемным кейсом и сравните с baseline: старые повторяющиеся рассуждения в истории могут влиять на повторный запуск.

Проверка с вашим Ascend endpoint и реальной Browse-прокси здесь не выполнялась. Съёмка проверяется через настоящий Pi nested-tool pipeline с тестовым screenshot tool официальной формы, а не реальной вкладкой. Для target-проверки используйте короткий кейс, затем длинный проблемный сценарий; сравнивайте с baseline на той же модели и вручную размеченным фактическим результатом.
