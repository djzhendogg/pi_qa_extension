# Фиксированный план и последовательные QA-подзадачи

Статус: реализация разрешена пользователем и добавлена в extension. Начальная инструкция декомпозиции содержит согласованные примеры; её настройка и проверка на реальной модели обсуждаются отдельно.

## Цель

Каждый QA run сначала формирует фиксированный план, затем выполняет подзадачи по порядку в общем agent loop Pi. После каждой завершённой подзадачи обязательны checkpoint и попытка screenshot. Модель квантованная: актуальное состояние должно быть коротким, однозначным и восстанавливаться из extension после compaction.

## Согласовано с пользователем

- Выбран фиксированный план, один общий контекст Pi, без отдельного агента на подзадачу и без собственных LLM-вызовов extension.
- План, текущий subtask_id и результаты хранятся в extension вне истории модели.
- Гранулярность следует исходной формулировке: «заполни и отправь форму» — одна подзадача; «выбери X в dropdown, введи Y в поле, отправь» — три подзадачи.
- Подзадача может включать несколько browser calls. Отдельный клик не является универсальной единицей декомпозиции.
- После каждой подзадачи сохраняется checkpoint и выполняется попытка screenshot, включая failed/blocked.
- Failed или blocked текущей подзадачи останавливает весь run; следующие подзадачи не выполняются.
- Входной сценарий передаётся JSON-строкой с scenario_id, url, task. Поля expected нет и не будет.
- Blocked — редкий крайний исход: обычные затруднения сначала разрешаются в текущей подзадаче, а не завершают run.
- Детальный промпт декомпозиции пока не согласован.

## Подходы

1. **Фиксированный план, общий loop Pi — выбран.** Переиспользует текущую extension и браузерную сессию; требует контроля переходов кодом и короткой актуальной инструкции для модели.
2. План с перепланированием. Удобен при неожиданном интерфейсе, но усложняет контроль исходной задачи. Не входит в выбранный вариант.
3. Отдельный агентный цикл на подзадачу. Изолирует контекст, но добавляет вызовы модели и передачу состояния. Не входит в выбранный вариант.

## Предлагаемые контракты

Следующие детали — предложения реализации, а не дополнительные требования пользователя.

Канонический вход — JSON-объект, который вызывающий код сериализует через JSON.stringify:

```json
{"scenario_id":"123","url":"https://example.com","task":"Заполни и отправь форму"}
```

Имя поля — scenario_id (исправление опечатки scenatio_id из примера). Все три поля обязательны и являются непустыми строками; url — полный HTTP(S) URL. Строка "http" сама по себе не является корректным URL. expected отсутствует в типах, валидации, контексте и отчёте. Не добавляется ни необязательный expected, ни скрытая замена под другим названием.

Предлагаемые способы ввода:

- В Pi: `/qa-run {"scenario_id":"123","url":"https://example.com","task":"Заполни и отправь форму"}`. Весь остаток команды разбирается как один JSON-документ, без разбиения по пробелам.
- При программном запуске: `--qa-case-json` со строкой JSON в одном элементе массива аргументов процесса, без сборки shell-команды.
- Существующие `/qa-run <path.json>` и `--qa-case <path.json>` можно сохранить для файлов с тем же новым форматом. Inline-объект определяется по начальной `{` после пробелов; некорректный JSON не интерпретируется повторно как путь. Одновременное указание обоих CLI-источников отклоняется.

Используется стандартный JSON с двойными кавычками, без eval и разбора JavaScript-выражений. Невалидный ввод не заменяет активный сценарий. Исходный task сохраняется без переписывания. qa_plan — инструмент сохранения результата декомпозиции моделью, а не самостоятельный LLM-планировщик.

```json
{
  "subtasks": [
    {
      "subtask_id": "S1",
      "description": "Click the Create button"
    }
  ]
}
```

- `qa_plan({subtasks})` валидирует и один раз сохраняет непустой упорядоченный план. ID — последовательность S1, S2, …; строки непустые, размеры ограничены. Повторный plan отклоняется без изменения сохранённого плана. Подзадачи содержат только subtask_id и description, без expected_result. Планировщик сохраняет явно заданные в task проверки и значения, но не придумывает бизнес-критерии успеха.
- `qa_execute_subtask({subtask_id})` активирует только следующую pending-подзадачу и возвращает её сохранённую description. Исполняет её модель через Browse в штатном loop Pi. Tool не запускает вложенный агентный цикл и не принимает переписанный текст действия. Повтор для уже активной подзадачи только возвращает её состояние; выполненное действие не запускается повторно.
- `qa_checkpoint({subtask_id, status, observation, reason})` завершает только активную подзадачу. status: passed / failed / blocked. Для passed нужно непустое observation, для failed/blocked — непустая reason. Повторное завершение подзадачи отклоняется без новой ревизии и screenshot. Старый накопительный completed и следующую цель модель больше не составляет: extension выводит их из плана и результатов.
- `qa_finish` сохраняется для общего результата после успешного выполнения всех подзадач. Итог основан на сохранённых результатах, отдельной стадии проверки expected нет. Passed запрещён, пока есть незавершённые подзадачи. Провал/блокировка подзадачи завершают run автоматически после диагностической попытки, без ещё одного решения модели.

Если сценарий стал невыполнимым во время активной подзадачи, используется её failed/blocked checkpoint. До принятого плана при невозможности продолжить допускается qa_finish(blocked), без passed и без фиктивной подзадачи.

## Значение результата без expected

- Passed означает: модель сообщила о выполнении всех действий и явно сформулированных в task проверок, с наблюдениями в checkpoint. Это не независимое подтверждение корректности бизнес-результата.
- Для действия модель проверяет его непосредственный наблюдаемый результат: например, выбранное значение dropdown или значение поля. Отсутствие tool error само по себе не является доказательством выполнения.
- Проверка вроде «убедись, что запись появилась» выполняется только если она задана в task. Для «нажми Отправить» не добавляются придуманные проверки БД, создания записи или конкретного текста уведомления.
- Failed — наблюдаемое невыполнение заданного действия или явно указанной проверки: например, после выбора dropdown осталось другое значение.
- Blocked — конкретное препятствие выполнению сценария: нужна авторизация, недоступна страница, потеряна связь с браузером или в task не хватает необходимых данных. Причина должна называть препятствие. Недостаток дополнительных проверок, которых нет в task, сам по себе не является blocked. Нельзя придумывать недостающие значения формы.
- Если после отправки формы потеряна связь с браузером, blocked описывает потерю связи и неизвестный исход действия. Отправка автоматически не повторяется, поскольку могла уже выполниться. Для task «нажми Отправить» дополнительное доказательство создания записи на сервере не требуется.
- Общая полнота декомпозиции остаётся ответственностью модели: проверка ID и порядка не доказывает, что qa_plan сохранил все требования task. Это отдельно проверяется при разработке промпта.

### Blocked как крайний исход

- Временная загрузка страницы, закрытый dropdown, элемент вне viewport, устаревший locator или единичная ошибка browser tool не являются основанием немедленно завершать подзадачу. Агент использует последнее наблюдение и выполняет адресное восстановление: короткое ожидание, scroll, открытие нужного элемента или обновление locator. Это часть текущей подзадачи, без изменения плана.
- Если причина выглядит устранимой, до blocked выполняется одна подходящая безопасная попытка восстановления и оценивается её результат. При сохраняющемся препятствии без новых оснований не запускаются циклические повторы. Очевидное требование внешнего вмешательства, например отсутствующие учётные данные или CAPTCHA, не требует бессмысленной попытки обхода.
- Неоднозначность формулировки сама по себе не означает blocked: используется очевидное толкование из task и доступного интерфейса, без придумывания обязательных значений и новых требований. Blocked допустим, если продолжение действительно требует отсутствующих данных, доступа или внешнего вмешательства.
- После ошибки связи сначала допустима безопасная попытка восстановить наблюдение текущего состояния браузера. Отправка формы, создание записи и другие действия с побочным эффектом не повторяются, если могли уже выполниться. При видимом результате выполнение продолжается; при сохраняющейся потере доступа к состоянию фиксируется конкретное препятствие.
- В reason для blocked указываются препятствие, выполненная попытка восстановления и её результат либо причина, по которой безопасной попытки нет. Это уточнение текста существующего поля, без новых обязательных полей контекста.
- Редкость blocked достигается восстановлением и узкими основаниями, а не квотой: подтверждённое невыполнение остаётся failed, неизвестный исход не объявляется passed. Временное затруднение до завершения восстановления не фиксируется как failed/blocked checkpoint.

## Состояние и порядок

Стадии: planning → ready → executing → checkpointing → ready / awaiting_finish → terminal.

- После загрузки кейса разрешены qa_plan и аварийный qa_finish(blocked); browser actions до сохранённого плана заблокированы.
- Ready разрешает qa_execute_subtask только для следующего ID. Executing разрешает browser tools и qa_checkpoint текущего ID.
- Awaiting_finish разрешает только qa_finish по сохранённым результатам; browser calls, новые подзадачи и изменение плана запрещены. Все требуемые наблюдения должны быть зафиксированы до завершения соответствующей подзадачи.
- Валидный checkpoint сначала закрывает допуск новых действий и сохраняет результат с ревизией, затем ожидает завершения диагностической попытки. После passed открывает следующую подзадачу или awaiting_finish. После failed/blocked сохраняет терминальный результат и закрывает run.
- Во время checkpointing допускается только внутренний диагностический вызов, связанный с текущим checkpoint; его нельзя перепутать с вызовом модели. Gate проверяет происхождение вызова, а не только имя screenshot tool.
- QA-инструменты sequential. Gate проверяет фактическое состояние на момент каждого tool call, включая смешанные пакеты. После терминального исхода используется существующее завершение пакета и abort на turn_end.
- Ошибка аргументов не меняет состояние и не завершает run. Ошибка записи отчёта переводит run в error и не открывает действия снова. Сбой Browse tool сам по себе не подменяется заявленным failed: модель фиксирует исход подзадачи; остановка loop без checkpoint остаётся техническим incomplete/aborted/error.

## Контекст квантованной модели

- Короткие постоянные правила описывают порядок tools; динамическая секция перед каждым запросом содержит стадию, текущий ID и номер из общего числа, description, последнее observation и допустимое следующее действие.
- Полный план и подробные результаты завершённых подзадач не вставляются повторно в динамическую секцию. Нужные значения предыдущих шагов могут оставаться в компактном сохранённом результате; лимиты и представление выбирает разработчик.
- Исходный кейс остаётся неизменным в extension и доступен в существующей системной секции; новая секция заменяет старую секцию прогресса, а не создаёт противоречащую вторую цель.
- Screenshot остаётся только человеческой диагностикой. Пиксели, base64 и пути не попадают в модельный контекст.
- Короткая секция не сокращает уже накопленную историю Browse. В первом варианте сохраняется штатная compaction Pi и восстановление состояния из extension; произвольное удаление tool-call/result пар не добавляется. Поэтому снижение размера всей истории не обещается. Отдельная политика сокращения истории требует последующего решения и проверки на реальной модели.

## Скриншоты и остановка

Переиспользуется QaDiagnostics: одна попытка screenshot после принятого checkpoint, существующая привязка к Browse tab, отдельные диагностические файлы и очистка изображений из контекста. Недоступный screenshot/tool/tab и ошибка сохранения изображения не отменяют checkpoint и не меняют verdict. Следующая подзадача допускается только после возврата диагностической попытки. Текущий timeout использует abort signal; backend должен его соблюдать, жёсткая отмена зависшего backend не гарантируется.

Для failed/blocked запрет обычных инструментов действует сразу после принятого checkpoint, до screenshot; терминальный статус выставляется после диагностической попытки. При пользовательском abort в этом промежутке сохраняется уже принятый исход подзадачи, повторная съёмка и выполнение действий не запускаются. Ошибки хранения имеют приоритет как технический error.

## Отчёт и совместимость

Предложение: schema_version 2, поля вердикта/телеметрии сохраняются, идентификатор сценария — scenario_id вместо case_id, сохранённый вход содержит scenario_id, url, task без expected. Добавляются план, стадия, active_subtask_id, упорядоченные результаты подзадач с observation/reason и checkpoint revision. Невыполненные подзадачи остаются pending; они не выдаются за выполненные. Ревизия связывает результат с существующим именем checkpoint-NNN в диагностике, без включения изображений и путей в QA-отчёт.

Verification остаётся agent_reported: gate проверяет порядок и наличие результата, но не доказывает истинность заявления модели. Старый контракт qa_checkpoint заменяется; README, CLI-примеры и tests обновляются вместе. Восстановление после перезапуска процесса, параллельные подзадачи, перепланирование и независимая проверка результата не входят в этот вариант.

Текущие parseTestCase/TestCase в src/qa-state.ts требуют id и expected; загрузка в src/qa-extension.ts читает только файл. При реализации обновляются оба пути загрузки, идентификатор отчёта и уведомления, системные правила, test-case.json, fixtures и проверки в test, README и встроенные инструкции запуска. Это несовместимое изменение входной схемы: старые кейсы необходимо перевести на новый формат. Сам механизм checkpoint/screenshot от удаления expected не зависит.

## Проверка реализации

- Валидация плана, неизменность исходного кейса, запрет замены плана и пропуска ID.
- Одинаковый разбор JSON-строки и файла: scenario_id/url/task без expected; текст с пробелами, кавычками и переводами строк сохраняется. Некорректный JSON, неполные URL и конфликт CLI-источников отклоняются без замены активного сценария.
- Запрет Browse до plan/активации; разрешение только актуального перехода; повторная активация не повторяет действий.
- Один принятый checkpoint и одна диагностическая попытка на подзадачу; следующая недоступна до завершения попытки.
- Failed/blocked сохраняют checkpoint, дают внутреннему screenshot пройти gate и блокируют следующие действия, включая siblings того же пакета.
- Финальный passed невозможен с незавершёнными подзадачами; пользовательский abort и ошибки записи не теряют принятый результат.
- Нет требования expected или expected_result и отдельной финальной браузерной проверки; явно заданные проверки task сохраняются в плане и observation.
- При проверке промпта: обычные затруднения приводят к адресному восстановлению, blocked содержит конкретное непреодолённое препятствие; неопределённая отправка не повторяется и не объявляется успешной без наблюдения.
- Контекст после compaction содержит правильную подзадачу и краткий прогресс без изображений; история tool calls остаётся валидной.
- Существующие typecheck и tests, обновлённые под новый контракт. Промпт декомпозиции отдельно проверяется на примерах обеих согласованных гранулярностей после его обсуждения.
