# Pi QA Goal Guardian — MVP 1

Статус: MVP 1 реализован после прямого указания пользователя писать код. Локально установлен Pi 1.5.2; выполнены typecheck и 25 тестов. Уточнения по установленному runtime и результатам независимого ревью находятся в `docs/implementation-notes.md`.

## Цель и границы

Сохранить исходную QA-задачу перед каждым запросом модели и завершать запуск явным `qa_finish`. Pi управляет agent loop, Browse и существующая MCP-прокси управляют браузером. Extension не вызывает LLM самостоятельно.

В MVP входят загрузка одного JSON-кейса, неизменное состояние исходной задачи, Goal Anchor, Stop Gate, JSON-отчёт и проверяемая телеметрия. Checkpointing, независимая проверка evidence, repeat guard и watchdog остаются следующими этапами. Нельзя обещать устранение повторов или подтверждённый успех до экспериментов и evidence verification.

## Подходы

1. Тонкая Pi extension — выбранная пользователем архитектура. Минимум логики, штатные hooks и tools; ограничения задаются доступными событиями Pi.
2. Отдельный SDK runner — дал бы больше контроля над запуском и остановкой, но добавил бы второй способ оркестрации. В MVP не нужен.
3. Изменение Browse Proxy — могло бы контролировать внутренние browser actions, но выходит за границы MVP и не требуется для Goal Anchor.

## Загрузка и жизненный цикл

Команда `/qa-run <path>` загружает один кейс с обязательными непустыми строками `id`, `url`, `task`, `expected`. URL должен использовать HTTP(S). Относительный путь разрешается от `ctx.cwd`. Ошибочный ввод не начинает запуск и не меняет предыдущий результат.

Для пакетного использования CLI-флаг `--qa-case <path>` загружает кейс при старте сессии; запуск модели инициируется обычным prompt Pi. Использовать тот же код валидации и состояния, что у команды.

Одновременно активен один запуск. Новый кейс не заменяет незавершённый. Каждому запуску выдаётся независимый `run_id`. Терминальное состояние блокирует инструменты до следующей явно загруженной задачи. Переход между Pi-сессиями очищает привязку к предыдущему запуску; активный запуск завершается как incomplete, без автоматического воспроизведения браузерных действий.

Тест-кейс хранится как неизменная копия. Состояние extension не зависит от сжатия истории. Восстановление запуска после перезапуска процесса не входит в MVP.

## Goal Anchor

`before_agent_start` добавляет короткие постоянные QA-правила к текущему системному prompt. `context` возвращает исходные сообщения плюс одно временное сообщение с `case_id`, URL, полными `task`/`expected` и инструкцией вызвать `qa_finish` сразу после проверки результата.

Anchor не сохраняется в историю Pi и не меняет тест-кейс. Добавляется в конец копии контекста, чтобы сохранять ранний префикс для caching; реальный выигрыш зависит от provider. В MVP нет фиктивного confirmed progress и автоматически придуманного current objective. Длинная исходная задача не обрезается молча.

## Результат и доверие к evidence

`qa_finish` принимает `verdict: passed | failed | blocked`, строку `evidence` и `reason`. Для passed обязательна непустая evidence; для failed/blocked — непустая причина. Такие проверки проверяют только форму заявления, а не его истинность.

Отчёт разделяет:

```json
{
  "schema_version": 1,
  "run_id": "generated-id",
  "case_id": "TC-001",
  "execution_status": "completed",
  "reported_verdict": "passed",
  "verification_status": "agent_reported",
  "verified_verdict": null,
  "evidence": "Success notification was displayed",
  "reason": ""
}
```

MVP не превращает заявление модели в verified passed. `execution_status` отдельно допускает `incomplete`, `aborted`, `error`; timeout зарезервирован для будущего реально наблюдаемого budget. Для технического завершения без `qa_finish` reported verdict остаётся null.

## Stop Gate

`qa_finish` регистрируется как sequential. После валидации он синхронно закрывает допуск новых инструментов, затем сохраняет результат. `tool_call` блокирует все последующие вызовы в QA-запуске, включая другие инструменты помимо Browse, чтобы не оставить обходной путь. Повторный finish не перезаписывает первый результат.

Обычный одиночный `qa_finish` возвращает `terminate: true`. В смешанном пакете инструменты до finish могут завершиться, последующие блокируются. После сохранения результата `ctx.abort()` в подходящей границе lifecycle используется как дополнительная остановка смешанного пакета; точное место выбирается по проверке установленного runtime, чтобы сохранить tool result и не допустить следующего provider request. Собственное завершение не переписывается как пользовательский aborted.

Ошибка записи не разрешает браузерные действия повторно и не обозначается успешным завершением; возвращается явная ошибка сохранения. JSON пишется во временный файл и переименовывается в уникальный итоговый путь, не содержащий произвольный case_id как путь.

Extension не может отозвать уже выполненные действия внутри одного Browse execute. Остановка процесса посреди действия также не является откатом side effect.

## Телеметрия

Сохраняются timestamps, duration_ms, число наблюдаемых основных provider requests (на проверенной границе Pi), запрошенных tool calls, начатых выполнений, заблокированных вызовов и результатов с ошибкой. Для llm_calls явно указать, учитывает ли используемый hook transport retries; не выдавать context-hook invocations за гарантированное число HTTP-запросов.

Неизмеряемые `post_success_actions`, `repeated_side_effects`, `goal_drift_events`, `success_rate`, `correct_verdict_rate` не заполняются нулями. Если нужны в схеме — null с указанием причины. Число попыток вызова после принятого finish — отдельная наблюдаемая метрика, не замена post_success_actions.

## Проверки реализации

- Невалидный кейс, обязательный expected, URL, сохранение исходного task.
- Anchor остаётся единственным временным сообщением и не меняет входные messages.
- Нет verified passed из произвольного текста evidence.
- JSON валиден, уникальные пути не допускают обход каталога через case_id.
- Терминальные результаты идемпотентны; ошибка записи не открывает gate.
- Реальный установленный Pi agent loop с детерминированным stream/mock provider, без платного API: finish отдельно; finish → browser; browser → finish → browser; двойной finish; невалидный finish; ошибка записи.
- В смешанных пакетах проверить отсутствие browser executions после finish и следующего модельного запроса; проверить корректность истории tool results.
- Обычное завершение без finish, ошибка модели и пользовательский abort дают технические результаты без выдуманного QA verdict.
- Повторный запуск и смена сессии не наследуют закрытый gate или чужие счётчики.

Полный E2E с Browse/Ascend возможен только в подключённом окружении. В README отделить локально проверенные гарантии от непроверенного поведения реальной браузерной интеграции.

## Решения, оставленные реализации

Точное разбиение модулей, формат сообщений ошибок, выбор тестового runner, граница вызова abort и обработка npm-версии определяются после проверки установленных типов и исходников. Эти решения не расширяют MVP.
